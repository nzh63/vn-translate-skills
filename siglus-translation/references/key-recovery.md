# 游戏密钥恢复手册

> 场景数据的 decrypt1 层需要 16 字节游戏密钥（见 `pck-format.md` §2）。
> 本手册给出从"最快路径"到"自己动手逆向"的完整决策树；工具是 `scripts/find_key.py`。
> 密钥属于**项目工作区**（如 `workspace/key.txt`），绝不写进技能脚本。

## 0. 决策树（按顺序尝试）

```
probe 不带 key → ExtraKeyUse=0？ ──是──▶ 根本不需要密钥
                     │否
1. 社区已知 key 表（hiroshil/SiglusEngine 的 KeyList.txt 收录数十款商业作品）
2. 同族游戏试 key（同一移植厂的作品常共享密钥片段，个别甚至整段相同）
3. find_key.py 明文滑窗模式（零依赖，秒级）
4. find_key.py 反汇编重组模式（需 capstone；实测对本仓库真机有效）
5. 动态工具兜底（skf.exe 跟随运行抓取 / x64dbg 手动跟踪 / xmoezzz 静态二层恢复）
```

每一步拿到候选后都走同一套**验证协议**：
`pck_tool.py probe --key-file` 通过 → 全量解包 0 失败 → 伪翻译冒烟上真机。

## 1. 密码学基础：为什么能逆

解包顺序 = 先异或固定表、再异或循环 key。场景块明文头部是
`[u32 压缩长][u32 解压长]`，且实测不变量 **压缩长 == 该块存储长度**。于是：

```
key[0:4] = cipher[0:4] ^ u32(块长) ^ 固定表[0:4]
```

这是纯密文即可算出的 4 字节真值（find_key.py 开头会打印它当自检）。剩下 12 字节
没有足够已知明文，纯密码学路线到此为止——必须看引擎二进制。

## 2. 引擎实现剖析（供举一反三）

对 SiglusEngine.exe 反汇编（x86 32 位）得到的完整图景：

```
.rdata 里存着两张 256B 固定表（scene 用 0xA21030，Gameexe 用 0xA20F30）
解密例程被编译器内联进调用者，形态:
    loop: al = [ecx + 表VA]        ← 解密2 循环头（引用固定表）
          [edx++] ^= al; ecx 环形递增(模256)
紧邻其前是解密1 的循环，密钥来自栈缓冲:
    mov al, byte ptr [0xa9ec07]    ← ★密钥字节散落在数据区各处！
    mov byte ptr [ebp-0x18], al       （取一个字节、放进栈槽）
    ……共 16 对这样的指令，槽位连续 [ebp-0x20 .. ebp-0x11]
    loop: al = [ebp+ecx-0x20]      ← 模16环形异或
```

**关键发现**：新引擎不把密钥连续存放，而是打散成 16 个孤立字节藏进数据区
（本作散布在 0xA9E4B5~0xA9EC07 共约 1.8KB 内），运行时逐条装入栈缓冲。
所以 §3 的明文滑窗扫不到——必须反汇编重组。find_key.py 模式 B 自动完成上述全过程。

## 3. find_key.py 用法与原理

```bash
python scripts/find_key.py Scene.pck SiglusEngine.exe --key-out workspace/key.txt [--verbose]
```

| 模式         | 依赖     | 做法                                                                          | 适用               |
| ------------ | -------- | ----------------------------------------------------------------------------- | ------------------ |
| A 明文滑窗   | 无       | 用 §1 公式推出前4字节，滑窗比对+全量验证                                      | 老/未混淆引擎      |
| B 反汇编重组 | capstone | 定位固定表→找循环头→回溯收集 `mov al,[imm]`×`mov [ebp+d8],al` 配对→按槽位重组 | 密钥打散存储的引擎 |

两模式的最终裁决都是同一验证器：**压缩长==块长 + 完整 LZSS 解压成功**（多场景复核），
误报会被直接过滤。实现要点与坑：

- 循环头编码有变体（`8A 81 <disp32>` 无 SIB / `8A 04 0D <imm32>` 带 SIB），
  以"imm32==表VA 且前面是 0x8A"识别，别写死 modrm。
- 线性反汇编在数据区会失步：find_key.py 在配对不足时分块重叠重解码取并集。
- 槽位基址不必假设 -0x20：对所有连续 16 槽窗口逐一重组、交验证器裁决。

## 4. 静态路线失败时的动态路线

- **skf.exe**（renanc1332/SiglusTranslationToolkit）：跟随游戏运行抓取，"run it and
  start the game" 即得 key。最省事，优先试。
- **x64dbg/cdb 手动法**：在文件读取返回处设断点 → 单步到第一个大循环 XOR →
  观察循环密钥缓冲区内容。慢但万能，也是给引擎出新变体时定位算法差异的办法。
- **xmoezzz/siglus_static_key_tool**：针对"二层派生"引擎（key 由运行时计算而非存储）
  的静态恢复工具。
- 若发现引擎算法本身变了（不是表异或而是别的变换）：先按 pck-format.md §2 校验
  已知好数据回归确认哪一层失效，再决定是否扩 crypt.py。

## 5. 同族观察（省时间的偏方）

社区 KeyList 中多款不同厂商作品共享密钥片段，例如
`円交少女 / 星織ユメミライ / 銀色、遥か` 三者的 key[2:6] 均为 `A6 00 5A 98`
（疑似出自同一家移植厂）。手头只有同族游戏时，先拿它们的 key 逐个试 probe，
命中就省掉整个逆向流程。
